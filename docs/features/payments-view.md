# PaymentsView

`frontend/src/views/PaymentsView.vue` (no Pinia store for data)

Payments page, built on Tailwind and the shared components: a "Record payment" dialog (STAFF and above), three slim figures, the 12-month "Collected by month" chart, a history the server pages, searches, filters and sorts (a bordered table card from `lg`, a ruled table from `md`, stacked list below), a receipt dialog with PDF download, CSV export. Route `/payments`, minimum role VOLUNTEER (`frontend/src/router/index.js`; see [../authentication.md](../authentication.md)).

## What the user sees
- Page head "Payments", lead "Record what members paid and see the history." From `lg` the head is the full-width band (title left, the buttons right, no lead) and the content sits in a padded area under it (see [../design.md](../design.md#layout)). STAFF and above also get two buttons: "Export CSV" (secondary) and "Record payment" (primary). A VOLUNTEER gets a read-only screen: no buttons, no dialog (the server answers 403 to their writes and exports).
- Figures row (only when there are payments, `StatTile slim` like the Overview's strip): "This month", "All time", "Average payment", read from `GET /api/payments/summary` (`{thisMonth, allTime, average, count}`, one aggregate query on the server) and shown with `formatMoney` ("$1,520.00"). "This month" sums payments whose `period` is the current month, not payments entered this month, so a back-dated payment never counts here. The browser never holds every payment; if the summary call fails the figures are left out and the rest works.
- "Collected by month" (only when there are payments), a bordered card (`CARD`, the same as the Overview ledger had) between the figures and the filters: the `CollectedChart` component draws twelve vertical columns, oldest to newest, scaled to the largest month (150px for the tallest), the amount above each column and the month (Nov, Dec ...) below, from `GET /api/dashboard/collected-by-month`. The head reads "November 2025 to October 2026, by the month the dues are for" with the twelve-month total on the right. The current month is a hatched, teal-outlined column, with a line under the chart saying it is still in progress. Amounts above the columns are whole dollars ("$1,250") from `md` up and abbreviated below it ("$1.3k", so 12 columns fit 390px); the columns and labels are `aria-hidden` and a visually hidden table lists every month with its exact amount. It loads itself; a failure shows "The monthly amounts did not load." with "Try again", and no payments in 12 months shows its own empty note. Recording a payment reloads it. It is no longer on the Overview.
- Filters (only when there are payments, or a filter is set): search, a Method select ("All methods" plus the 7 methods), "Clear filters" when one is set, and a count line ("32 payments", or "3 of 32 payments" when filtered; the second number is the summary's `count`). Search is sent to the server 300 ms after the last key (Enter sends it at once), trimmed, with at most 100 characters: it matches part of the member's name (any case) or a receipt number ("R-000141", "000141" or "141", an exact match). A Method change, a new search, a sort or a size change all go back to page 1. From `lg` they are one 32px row with the labels visually hidden: search on the left, "Clear filters" after it, Method on the right; the count moves to the table card's footer (the line stays for screen readers).
- History, one server page at a time, newest first by default (paid on descending, then id descending). The headers Paid on, Member, Month and Amount are buttons (`SortButton`) that sort on the server: the first click starts in the column's natural direction (Paid on, Month and Amount newest or highest first, Member A to Z), a second click flips it, `aria-sort` on the `th` says which column and which way, and the caption says "Sorted by Paid on, newest first". Below `md` there are no headers, so the phone list keeps the sort the URL holds (newest first unless a link says otherwise). From `lg` it is a bordered card with a grey header row; its footer holds the `Pager` and a line (the count only while the pager is hidden, "Sorted by Paid on, newest first" on the right), columns Receipt (a text button "R-000012" that opens the receipt dialog), Paid on, Member, Month, Method, Amount (right aligned); it scrolls sideways inside the card when narrow. From `md` to `lg` (and below as a stacked list) the earlier layout stays: Paid on, Member, Month covered ("Oct 2026", `periodLabel`), Method (label), Amount (right aligned, tabular), Receipt (a text button "R-000012" that opens the receipt dialog).
- Paging: `Pager` in server mode (it only needs the total, `totalElements`): the card footer from `lg`, under the list or table below `lg`; 25 rows a page, sizes 10, 25, 50 and 100, hidden at 10 payments or fewer, and the Rows per page select stays whenever there are more than 10 ([../design.md](../design.md#pager)). A link to a page past the last becomes the last page.
- While a page loads the rows on screen stay, dimmed (`opacity-60`, `aria-busy`) with a visually hidden "Updating payments..." status, and the new rows replace them when they arrive. Only the newest request may change the screen: a slower, older answer is dropped.
- URL: `?page=2&size=50&search=keb&method=CHECK&sort=amount,asc`, each left out when it is the default (page 1, 25, no search, any method, `paymentDate,desc`), written with `router.replace` so Back and a refresh keep the place; `memberId` is not part of it. A link from outside (`/payments?search=`, a bare `/payments`) is read back into the screen.
- Empty states: no payments "No payments yet. Record the first one." (with a "Record payment" button for STAFF and above); filters match nothing "No payments match these filters." with "Clear filters"; a load failure shows a banner "The payments did not load. Check your connection and try again." with "Try again".

## Record payment dialog
`BaseModal` md (a full-screen sheet below `lg`, see below), STAFF and above only. Fields: Member (the searchable `MemberPicker`, see below, over ACTIVE members only; with no active members the dialog shows an `EmptyNote` and the submit button is disabled), Month covered (`type="month"`, default and `max` the current month), Paid on (`type="date"`, default and `max` today, hint "Change this when you enter an older payment."), Amount (`min` 0.01, step 0.01), Payment method (7 methods, default Cash), Notes (optional, 500 characters, counter).
- The body is built only by `buildPaymentRequest(form)` -> `{ memberId: Number, amount: Number, paymentMethod, period, paymentDate?, notes? }`; `paymentDate` and `notes` are left out when blank (`frontend/src/utils/paymentPayload.js`).
- Member picker (`frontend/src/components/MemberPicker.vue`, search in `frontend/src/utils/memberSearch.js`): an ARIA 1.2 combobox, placeholder "Search by name, phone or email". Typing filters the active members, ignoring case and accents, on name, email and phone (a query of only digits, spaces, "+", dashes and brackets matches the phone by its digits); every word typed must appear in the name or email. Results are ordered name starts with the text, then a name word starts with it, then the rest, ties by name. The list shows 8 rows and a "N more, keep typing" line; with no match it says "No member matches 'xyz'"; a visually hidden live region says "N results; use arrow keys". A row is the name, a muted line with the household name and phone when known, and a dues badge on the right: "3 months behind" (clay, the server's `consecutiveMonthsMissed`), "Due this month" (ochre) or "Paid up" (fern), the last two read from the same year strip rule on the paid months the dialog loads when it opens (`GET /api/payments/paid-months?months=12`, `duesBadge` in `utils/dues.js`); until they have loaded a row only says "N months behind". Keys: the list opens with no row highlighted (no `aria-activedescendant`); Arrow Down (opens, then highlights the first row) and Arrow Up (the last row) move and wrap, Home and End (first and last row while open), hovering a row highlights it; Enter picks the highlighted row, or the single result when there is exactly one, and with several results and no highlight does nothing (with the list open Enter never submits the form; with it closed it does), Escape closes the list (with it closed Escape reaches the dialog), Tab closes it. The list opens on click, typing or an arrow key, not on focus. Once a member is chosen the input shows the name read-only with a clear button (Backspace or Delete does the same) that returns to searching. Focus lands on the picker when the dialog opens because `BaseModal` focuses the first field. The list is drawn fixed under the input and placed inside the dialog element, so the scrolling dialog body does not clip it; it flips above the input when there is more room there and follows scroll, resize and the on-screen keyboard.
- Choosing a member fills an empty Amount with that member's most recent payment (paid on then id), so a regular amount is one tap; the amount comes from `GET /api/payments/member/{id}` (`api.getPaymentsByMember`), fetched when the member is chosen, and an answer for a member chosen earlier, or one that arrives after the user typed an amount, is dropped. Only an empty Amount, or one the picker filled earlier, is replaced: what the user typed stays; clearing the member empties an amount the picker filled.
- Client checks (`validateForm`): member chosen, month not in the future, date not in the future, amount at least 0.01, notes at most 500.
- Server errors (`showSaveError`): `error.fieldErrors` `[{ field, message }]` go under their fields; a 400 without a field goes into an `AlertBanner` at the top of the dialog and an error toast "Could not record payment" (no toast for 403, the shared API handler already shows one). The dialog stays open on failure.
- Success closes the dialog, resets the form (month and date back to the defaults), reloads the current page, the figures, the members (a payment resets their months-behind count) and the chart, and shows the toast "Payment recorded" ("Jane Smith, Mar 2024: $50.00").

## Record payment on a phone
Below `lg` the same `BaseModal` is a full-screen sheet (`sheet` prop, see [../design.md](../design.md#layout)): Back and the title in a dark top bar, the form scrolling, and a pinned bottom bar with "Record payment" (48px, primary) over "Cancel". Controls are 48px high and 16px text, so iOS does not zoom. The desktop dialog is unchanged.
- Once a member is chosen a card under the Member select shows the name, the large year strip and one sentence from `owedSummary` (`frontend/src/utils/dues.js`), built from the same `stripCells` rule as the Members list: "Owes July, August and September 2026. October is due now." (months the server counts as missed, then the current month if unpaid); "Paid up to last month. October is due now."; or "Paid up. Nothing is owed for October 2026." when nothing is owed. The strip uses the same paid months (the card is left out until they have loaded, or if that call failed, because the strip would show wrong squares); if they arrive after a member was chosen (the `?memberId=` deep link), Month covered is set again by the same rule.
- Choosing a member (the picker or `?memberId=`), on any screen width, sets Month covered to their oldest missed month and shows the hint "July 2026, the oldest month not paid." while the field still holds that month; when only the current month is due, or the member is paid up, the month stays the current one with no hint, and a month changed by hand afterwards is never overwritten. Months older than the strip's 12-month window are not counted.
- Unlike the mockup the member is still chosen in the form (the Payments tab opens the sheet with no member); the deep link below fills it. On the sheet the picker's input is 44px high with 16px text (48px like its sibling fields through `max-lg:min-h-12`), the clear button 44px, and each result row at least 44px; the result list opens under the input, inside the sheet.

## Deep link
`/payments?search=<name>` (the member page's "All payments") starts with that text in the search box and in the first request.

`/payments?memberId=<id>` (the Members phone card's Record payment link) opens the Record payment dialog with that member chosen. After the first load (page, figures and members) `openForQueryMember` removes the parameter from the URL (`router.replace`), so a reload or closing the dialog does not reopen it, then, for STAFF and above only, opens the dialog and sets `form.memberId` when the id is an active member (a member who does not owe dues leaves the picker empty). A VOLUNTEER, or a failed members load, just gets the plain screen. The rest of the screen is unchanged by the redesign: the dark-teal rail only changes the frame around it.

## Receipt dialog
`ReceiptDialog` (`frontend/src/components/ReceiptDialog.vue`, also used by [the member page](member-detail-view.md)): a `BaseModal` sm titled "Receipt R-000012". Shows Receipt, Member, Month covered, Paid on, Method, Notes (only when present) and the Amount, inside a plain element (`receiptContent`) that html2pdf captures: only token hex colours, no tinted or blended colours. "Download PDF" imports `html2pdf.js` on first click, letter portrait, file `receipt-R-000012.pdf` (`PaymentsView.vue`); "Close" closes it. A PDF failure shows the toast "Could not create the PDF".

## Endpoints
Calls made through `frontend/src/services/api.js`:

| Method | Path | api.js | Used by |
|--------|------|--------|---------|
| GET | `/payments/page?page&size&search&method&sort` (`page` zero-based) | `getPaymentsPage` | `loadPage` (the history) |
| GET | `/payments/summary` | `getPaymentSummary` | `loadSummary` (the three figures) |
| GET | `/payments/paid-months?months=12` | `getPaidMonths` | `loadPaidMonths`, when the Record payment dialog opens |
| GET | `/payments/member/{id}` | `getPaymentsByMember` | `prefillAmount`, when a member is chosen |
| GET | `/members` (STAFF and above only; a VOLUNTEER does not load it) | `getMembers` | `loadMembers`, for the Member picker |
| POST | `/payments` (STAFF+) | `createPayment` | `recordPayment` |
| GET | `/payments/export` (blob, STAFF+) | `exportPayments` | `exportPayments` |

Backend: [payment-controller.md](payment-controller.md). Rules the server enforces: any past month up to 10 years back is valid (a future month is a 400); `paymentDate` is optional, must not be in the future, and a back-dated payment never moves the member's last-payment date backwards; a member whose status is not MEMBER is refused with `MEMBER_008` ("Member '<name>' is inactive. Reactivate the member before recording a payment."); a second payment for the same member and month is refused ("Member '<name>' already has a payment recorded for period <YYYY-MM>"). The request shapes are tested against the shared fixtures `src/test/resources/contracts/record-payment-request.json` and `record-payment-request-backfill.json` (`frontend/src/__tests__/utils/paymentPayload.test.js`).

## State and helpers
Local component `data()` plus the `queryPaging` mixin (`page`, `pageSize`, `setPage`, `setPageSize`, `resetPage`, `settlePage`): `members`, `membersLoaded`, `membersError`, `payments` (the one page; `[]` when the response has no `content`), `total` (`totalElements`), `summary` (null until loaded or when it failed), `paidByMember` (null until the dialog has loaded the months), `loaded`, `loading`, `loadError`, `searchText` (the box) and `search` (what the list was asked for), `method`, `sort` (`{field, direction}`), `recordOpen`, `form`, `formError`, `formErrors`, `saving`, `today`, `selectedPayment`, `receiptOpen`. `requestKey` (the request parameters as JSON) is watched: any change loads the page again, and nothing else does. `pageRequest` and `prefillRequest` are plain counters that make the newest answer win. `setup()` exposes the stores and the formatting helpers.

Pure helpers in `frontend/src/utils/paymentQuery.js` (tested in `frontend/src/__tests__/utils/paymentQuery.test.js`): `parseSort`, `formatSort`, `nextSort`, `ariaSort`, `sortLabel`, `readFilters(query)` and `filtersQuery(filters)` (URL to state and back, defaults left out), `pageParams(...)` (the request: 1-based page to the server's 0-based, trimmed search, empty search and method left out). In `frontend/src/utils/paymentHistory.js` (tested in `paymentHistory.test.js`): `periodLabel('2026-10')` -> "Oct 2026", `receiptNumber(payment)` -> `R-` plus the id padded to 6 digits (derived: the backend has no receipt number), `methodLabel`, `sortPayments` (newest first, used for the member's payments). `paidMonthsFromMap` is in `utils/yearStrip.js`. `formatMoney` lives in `frontend/src/utils/index.js` and is shared with the Overview. `PAYMENT_METHODS` is in `frontend/src/utils/paymentPayload.js`. The view's behaviour (parameters sent, debounce, sort click, stale answers, error and retry, dimmed rows, the amount prefill) is tested in `frontend/src/__tests__/views/PaymentsView.test.js`.

## Side effects
- Triggers a file download for CSV and PDF
- Recording a payment re-fetches the current page, the figures, the members and the chart

## Gotchas
- The table and receipt read the nested `payment.member?.name` (falls back to "Unknown").
- Sorting is by the column headers only, which exist from `md`; on a phone the list keeps the sort in the URL. A header sort goes through the server, so Member sorts by name ignoring case, and rows with equal values keep a stable order (newest id first).
- The month input is a native `type="month"`; browsers without it show a text box, and the server still validates `YYYY-MM`.
